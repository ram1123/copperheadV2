## 1. Luminosity — 2025 and 2026

Cross-checked `configs/parameters/lumi.yaml` and `stage3/make_datacards.py`'s `lumi_syst` dict
against `.claude/skills/cms-object-guidelines/references/lumi.md` (LUM POG `LumiRecommendationsRun3`,
verified via user 2026-09-01) and the existing
`.claude/reports/investigations/2026-09-03_run3-datasets-lumi-2024-2026.md`.

- **2025 total**: `lumi.yaml:14` = 110,840.0 pb⁻¹ (110.84 fb⁻¹), sourced to PdmVRun3Analysis. Matches
  the 2026-09-03 report. **Open discrepancy** (unresolved by this pass): sum of per-era `lumi_pb` in
  `dataset_nanoAODv15_run3.yaml` = 110,850.0 pb⁻¹ (10 pb⁻¹ higher), and the LUM-POG-reference PdmV
  Golden-JSON table gives era C-G = 110.38 fb⁻¹ / B-G = 110.63 fb⁻¹ — neither exactly matches
  110.84/110.85. `lumi.md` §8.1 explicitly flags 2025 as needing re-derivation from the golden JSON
  with `normtag_BRIL.json`; not done here. Small relative to the 5% overall 2025 uncertainty, but an
  internal-consistency item worth closing before a final 2025 result.
- **2025 uncertainty**: **5%, uncorrelated** with 2022-2024, per LUM POG (`lumi.md` §2, S1),
  preliminary (Z-counting vs partial-vdM tension, updated Feb 2026). This was **missing** from
  `stage3/make_datacards.py`'s `lumi_syst` dict this session (`KeyError: '2025'` on a real
  `run_stage3_vbf.py` run) — fixed earlier this session by adding `"2025": {"lumi2025": 5.0}` with a
  comment citing this source; not re-verified as "still fixed" in this pass but no reason it
  wouldn't be (that file wasn't touched by the profile churn described in §0).
- **2026 total**: `lumi.yaml:15` = 25,950.0 pb⁻¹ (eras A+B+D; era C low-PU excluded), matches the PdmV
  Golden-JSON table exactly (no discrepancy, unlike 2025). Explicitly "Preliminary Offline Results."
- **2026 uncertainty**: **none exists yet** per LUM POG (`lumi.md` §2/§8.1: "2026 has no uncertainty
  available yet ... flag any 2026 result"). Consequence: `lumi_syst` has **no `"2026"` entry**. A
  `run_stage3_vbf.py` run for year 2026 will hit the *same* `KeyError` pattern just fixed for 2025 —
  per the stored reference, this should **not** be patched with an invented number; it should remain
  a hard failure until an official LUM value exists, and the person running it should be told why.

## 2. MC datasets / cross-sections — 2025 and 2026

- **One physical MC set for 2024/2025/2026.** Every 2025 and 2026 MC sample (DY×6, Top×2, VV×7,
  EWK×2, Higgs×3) uses `RunIII2024Summer24NanoAODv15` (2024-conditions simulation); the 2025 MC block
  is byte-identical to 2024's (same DAS paths, `cross_section_pb`, `kfactor`); the 2026 block is the
  same active samples with skipped placeholders dropped. **No 2025- or 2026-conditions central
  NanoAODv15 campaign exists yet** — confirmed unchanged from the 2026-09-03 report.
- **Cross-sections are not sourced from `configs/parameters/cross_sections.yaml`** for Run 3 — that
  file has **zero** explicit `'2025'`/`'2026'` keys (checked directly this pass). Run-3 samples carry
  `cross_section_pb`/`kfactor` embedded per-sample in `configs/datasets/dataset_nanoAODv15_run3.yaml`
  instead, and those are confirmed identical across the 2024/2025/2026 blocks. **Not a gap** — a
  different, internally-consistent code path — but worth noting so the empty `cross_sections.yaml`
  Run-3 rows aren't mistaken for a missing value.
- **Consequence for data/MC agreement**: since 2025/2026 physics relies on year-specific JME/MUO/LUM
  correction payloads to absorb the conditions difference from reused 2024-conditions MC, and (per
  §3 below) the MUO/LUM payloads for 2026 are themselves placeholders reusing 2025/2024, the
  approximation compounds specifically for 2026. Not independently re-verified this pass; carried
  from the 2026-09-03 report.
- **2026 data**: real PromptReco eras A, B, D active; era C (low-PU) correctly `skip_sample: True`
  and excluded from `total_lumi_pb`. Uses 4 Muon primary datasets (`Muon0`-`Muon3`) vs 2
  (`Muon0`/`Muon1`) for 2024/2025 — **still unverified**: whether prestage/DAS resolution handles the
  4-PD case correctly.
- **`vbf_aMCatNLO`/`vbf_powheg` base+`ext1`** — both signal samples list a base + `_ext1` dataset for
  2025 and 2026 (as for 2024). **Still unverified**: whether stage-1 `sumGenWgts`/normalization
  correctly sums base + ext1. This would systematically bias the ggH/VBF signal normalization if
  mishandled — higher-priority to close than most other open items here, since it directly affects
  the measured signal strength rather than being an unused/placeholder path.

## 3. `switches.yaml` vs CMS POG recommendations — 2025 and 2026

Full delegated review below (physics-reviewer agent, independently spot-verified: `do_jet_horn_ptcut`
values and `jec_unc_to_consider["2025"]` vs `["2026"]` both directly re-checked by the main agent
against the live files and confirmed as reported).

### Ranked findings

1. **[HIGH] `do_jet_horn_ptcut` is `false` for 2024, 2025, *and* 2026** (`switches.yaml:227-237`) —
   contradicts the switch's own inline comment (`:220-226`, "2024: HE still needs pT>50 ...
   2025/2026: treated the same as 2024") and the official JME HE-region mitigation recorded in
   `cms-object-guidelines/references/jets.md` §5 (source: JME "Mitigation techniques" slide, Anna
   Benecke slide 14; also `jme-horn-region-official-recommendation` memory). `jets.md` and
   `switches_profiles/nominal_nozpt_jme_reco.yaml`'s own comment both still assert the value should
   be `50` for 2024-2026. Combined with `jer_strat=4`'s "no stochastic smearing for unmatched jets"
   being the *other* half of the same two-part official mitigation, **the HE region currently has no
   forward-jet pT threshold applied at all**, for any year in this file. Does not look like a profile
   application (no stored profile sets exactly this combination) — looks like a manual edit outside
   the profile mechanism. **Needs owner confirmation**: intentional change, or restore `50` and
   rerun the sync-stage1 regression check.
2. **[MEDIUM, latent] 2025 JEC uncertainty source labels reuse `2024`** — `jec.yaml`
   `jec_unc_to_consider["2025"]` = `Absolute_2024, BBEC1_2024, EC2_2024, HF_2024, RelativeSample_2024`
   (verified directly), while `["2026"]` correctly uses `*_2026`. Latent today because
   `do_jec_unc=false` for 2025 in the nominal baseline, but `switches_profiles/syst.yaml` (the
   documented "Scenario 4: full systematics production run") sets `do_jec_unc: true` — applying that
   profile for a 2025 systematics run would look up `_2024`-suffixed correction keys against the 2025
   `jet_jerc.json.gz` payload, either failing outright or silently applying the wrong year's JES
   per-source split. **Must fix to `_2025` before any 2025 full-systematics production run.**
3. **[MEDIUM] `switches_profiles/nominal_nozpt_jvm_jets.yaml` uses jet-level, not event-level, jet
   veto-map removal** (`filterEvents: false` / `filterJets: true`, verified directly) — the nominal
   baseline (`filterEvents: true` / `filterJets: false`) correctly matches the Run-3-mandatory
   event-level rejection in `jets.md` §6.2, but this alternate profile reverts to the Run-2
   prescription. The profile's own header frames it as a validation/comparison scenario; confirm it's
   never applied as the *production* config for a final 2025/2026 result.
4. **[Authoritative verification required / unchanged since 2026-09-03]** — re-verified, all still
   open: 2025 Rochester payload provenance not pinned in-repo (`muons.md` `[Verify]`); EBE
   mass-resolution BS calibration for 2025 *and* 2026 both literally the 2024 file, MC key pointing at
   the Data-derived JSON; Run-2-derived NNLOPS applied to Run-3 ggH with no Run-3-specific ratio
   validated; JER `ScaleFactor`/`SFUncertainty` schema assumption unchecked against the real
   2025/2026 payload (matters once `do_jer_unc` is turned on, i.e. under `syst.yaml`); MET-filter list
   (`ecalBadCalibFilter`) differs 2024 (in) vs 2025/2026 (commented out); b-tag UParT loose/medium WPs
   for 2025 copied from 2024, 2026 copied from 2025 (`# PLACEHOLDER ... pending BTV POG WPs`) —
   affects `nBtagLoose`/`nBtagMedium` selection counting even with `do_btag_wgt` off; PU-DNN model dir
   and Z-pT reweighting params for 2025/2026 both explicit placeholders (features themselves off, so
   no live impact yet); all 2026-specific MUO/LUM placeholders (Rochester, muon SF, pileup weights)
   and the single-JER-tag (RunBD) limitation for 2026 era C — all reconfirmed unchanged.
5. **[Compliant, no action]** — `do_jet_veto_maps_filterEvents/filterJets` nominal baseline; `jer_strat
   = 4` for 2025/2026; `do_pu_wgt = true` for 2025/2026; muon correction *ordering*
   (BS-constraint → Rochester → trigger-match → FSR) for 2025/2026 matches `muons.md`.
6. **[Optional improvement]** DeepJet/ParticleNet b-tag WPs in `jet.yaml` are unset (`0.000`) for all
   Run-3 years — dead config since the analysis reads `btagUParTAK4B`, not currently a live bug but
   worth removing or marking clearly unused.
