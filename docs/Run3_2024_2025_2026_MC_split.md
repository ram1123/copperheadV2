# 2024 / 2025-26: year grouping and Summer24 MC split

## Guideline

From the CMS Physics Coordination report (PC meeting, 26 August 2026, "New analyses" slide):

- New analyses should start on 2024 and 2025/26 data.
    - **2025 and 2026 are treated as one single year** (with different data-taking eras).
    - **The same MC ("Summer24") is used for 2024 and 2025/26.**
- Searches and stats-limited measurements (H→µµ is one):
    - approvals in Q3/Q4 2026 should include 2024 data;
    - approvals in 2027 **must use the full Run 3 (2022–2026)**.

How this analysis applies it:

1. **2025 + 2026 form one year ("2025/26")**, split into their data eras.
2. **The Summer24 MC is shared between 2024 and 2025/26, split by luminosity fraction.** Each MC event
   is used in exactly one year, and each year's share is normalized on its own. The same events are
   not re-weighted into every year.

## Why the MC has to be split

`configs/datasets/dataset_nanoAODv15_run3.yaml` lists the **same** `RunIII2024Summer24NanoAODv15`
files under the 2024, 2025 and 2026 blocks, so the plain prestage JSONs
(`prestage_output/processor_samples_<year>_NanoAODv15.json`) all have identical MC file lists. If
stage-1 runs on those, every MC event is processed three times, once per year, scaled to that year's
luminosity:

- the **total normalization is still correct** (xsec × lumi(year) / sumGenWgts per year);
- but the per-year MC templates are **built from the same events**, so they are 100% statistically
  correlated rather than independent. Treating them as independent in the fit is wrong.

> **Status as of 30 Sep 2026:** every compacted v15 production so far (all `Aug30` and `Sep22` labels,
> including `..._OfficialRecomendation_Systematics` and `..._IPAdditionalLepVeto`) was run with the
> **full** MC in each year (`fraction == 1.0` in the parquet). The results must be re-run with the
> lumi-split MC to follow the guideline (MC only; data is unaffected).

## Implementation

| Piece | What it does |
| ----- | ------------ |
| [scripts/split_prestage_by_year_lumi.py](../scripts/split_prestage_by_year_lumi.py) | Splits every MC sample's files into disjoint 2024 / 2025 / 2026 buckets by lumi share; copies each year's data unchanged from its own prestage JSON; writes `prestage_output/processor_samples_<year>_NanoAODv15_LumiSplit.json`. Never overwrites an input. |
| `run_stage1.py --prestage-tag <tag>` | Reads `processor_samples_<year>_NanoAODv<v>_<tag>.json` instead of the plain file. |
| `PRESTAGE_TAG` env var ([common_workflow.sh](../common_workflow.sh)) | Passes `--prestage-tag` through `run_analysis_pipeline.sh -m 1`. |
| `prestage_tag` in [workflow/config.yaml](../workflow/config.yaml) | Same, for the Snakemake `stage1` rule. |
| `getSavePath` in `run_stage1.py` | Samples with `split_provenance` are written to `f1_0/` (not `f0_xxx/`), so compaction and every `f1_0` reader work unchanged. Debug-fraction runs still go to `f0_xxx/`. |

### How the split works

- For each MC sample, files are sorted by name and assigned contiguously by cumulative event count
  (`num_entries`) to buckets matching the lumi shares. Every bucket gets at least one file when there
  are enough files. The split is deterministic: the same input always gives the same split.
- `sumGenWgts`, `nGenEvts` and `sumLHEPdfWgts` are **recomputed per bucket** from each file's `Runs`
  tree (not scaled from the total), so each year's MC is normalized by its own files:
  `weight = xsec × lumi(year) / sumGenWgts(bucket)`.
- Because the split is at file level, each sample's event share only approximately matches the lumi
  share: within 0.5 % for the large samples, up to about 2.7 % for samples with few files (e.g.
  `ggh_powhegPS` has 6 files in 2026). This does **not** bias normalization; it only changes how the MC
  statistics are shared between the years.
- Output metadata per MC sample:
    - `fraction`: this bucket's share of the sample's generated events (a `fraction` column also ends
      up in the parquet);
    - `split_provenance`: source JSON, lumis, fractions, bucket year, git commit/dirty state, timestamp.

## Step-by-step

### 0. Prerequisites

- Up-to-date **plain** prestage JSONs for 2024, 2025 and 2026 (`run_analysis_pipeline.sh -m 0`). The
  2024 one is the MC source; each year's own file provides that year's data.
- A valid VOMS proxy: the split reads the `Runs` tree of every MC file (about 9,700 files) over XRootD.

### 1. Preview the split (no file reads, nothing written)

```bash
./run_in_pixi.sh default python scripts/split_prestage_by_year_lumi.py --dry-run
```

Check the log for the per-sample file counts and for warnings: an MC file list that differs between
years, or a sample with too few files.

### 2. Write the split JSONs

```bash
./run_in_pixi.sh default python scripts/split_prestage_by_year_lumi.py --n-workers 20
```

Produces `prestage_output/processor_samples_{2024,2025,2026}_NanoAODv15_LumiSplit.json`. Useful
options: `--years`, `--mc-source`, `--data-source '<template with {year}>'`,
`--output '<template with {year}>'`, `--lumi-yaml`.

### 3. Run stage-1 on them

Snakemake (use a **new** `run_tag`, so the split-MC output doesn't mix with a full-MC label):

```bash
snakemake -s workflow/Snakefile all_stage1 -j 2 --resources gateway=1 --rerun-incomplete --restart-times 3 --latency-wait 60 \
  --config use_gateway=True prestage_tag=LumiSplit 'years=["2024","2025","2026"]' \
  run_tag=FilterEvents_Sep22_tightPassLepVeto_OfficialRecomendation_LumiSplit
```

Or directly:

```bash
PRESTAGE_TAG=LumiSplit bash run_analysis_pipeline.sh -m 1 -k -y 2025 -v 15 \
  -c configs/datasets/dataset_nanoAODv15_run3.yaml \
  -l Run3_nanoAODv15_FilterEvents_Sep22_tightPassLepVeto_OfficialRecomendation_LumiSplit
```

The stage-1 log prints `Prestage sample file: ..._LumiSplit.json`; check it to confirm which file was
used. Afterwards, the MC parquet `fraction` column is about 0.445 / 0.449 / 0.105 for 2024 / 2025 / 2026,
not 1.0.

### 4. Compact, stage-2, stage-3

No changes needed: they run per year as before (`prestage_tag` only affects stage-1).

### 5. Treat 2025 + 2026 as one year at stage-2/3 (planned, not implemented yet)

Stage-1 deliberately keeps 2025 and 2026 as separate years, so that each keeps its own data
corrections (JEC, golden JSON, jet veto maps) and pileup profile. The guideline's "one year" is meant
to be applied downstream:

- add a `2025_2026` pseudo-year that **adds** the 2025 and 2026 histograms into one set of templates,
  with one set of year-uncorrelated nuisances;
- this is different from the existing `Run3` pseudo-year in `run_stats_pipeline_VBF.sh`, which
  *combines* separate per-year cards.

Until this is implemented, 2025 and 2026 appear as separate years in the datacards. The nuisance
correlation scheme for the merged year still needs to be agreed before implementing it.

## Caveats

- **Stale split JSONs:** re-running prestage (`-m 0`) regenerates only the plain JSONs. Re-run the split
  afterwards, or the `_LumiSplit` files will be stale.
- **Old two-bucket files are superseded:** `processor_samples_2024_NanoAODv15_Fraction.json` and
  `processor_samples_2025_2026_NanoAODv15.json` come from an earlier 2024 vs 2025_2026 version of the
  script. They have no 2025/2026 data and use the old `f0_xxx` output layout. The only run that used
  them (`FilterJets_Sep22_*`/2024) left `f0_445`…`f0_464` directories that were never compacted.
- **Sync / CI:** `--sync` still reads `processor_samples_<year>_NanoAODv<v>[_<tag>]_sync.json`; the
  sync references are unaffected unless a tag is set.
